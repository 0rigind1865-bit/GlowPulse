# GlowPulse 改進計劃

> **依據**：第一性原理分析（2026-06-06）＋ 健診報告（2026-04-19）
> **排序原則**：依「對真實獲客的槓桿」而非「工程難度」排序。
> **狀態標記**：⬜ 未開始 ／ 🟦 進行中 ／ ✅ 完成

本計劃對應分析中的四個根本問題：

| 編號 | 根本問題 | 一句話 |
|---|---|---|
| R1 | 槓桿配置反了 | 力氣全花在廣播，能撬動分發的「主動出擊」卻不能跑 |
| R2 | 迴路對噪音學習 | 互動信號近乎全零、且把結果錯誤歸因給文案 |
| R3 | 測量虛榮指標 | 評分漏掉回覆（最高價值的意圖信號），與營收脫鉤 |
| R4 | 靜默失效 | 自主代理在真實世界行動，卻不回報結果 |

---

## 階段總覽

| 階段 | 主題 | 預估 | 何時做 |
|---|---|---|---|
| **P0** | 立即止血：停空跑、修測量、加告警 | 0.5–1 天 | 現在 |
| **P1** | 拆掉結構性脆弱：設定脫離程式碼、迴路設信號閘門、接真實指標 | 2–4 天 | 兩週內 |
| **P2** | 校準投資與長期：出擊管道、瘦身、測試、內容策略 | 持續 | 規劃中 |

## P0 — 立即止血（高槓桿、低成本）

### ⬜ P0-1　停掉空跑的 engage 排程，並讓權限失敗「說出來」
- **對應**：R1、R4
- **為什麼**：`engage` 缺 `threads_manage_replies` 權限，`getPostReplies()`（`threads.ts:689`）對 403 靜默回傳 `[]`，導致每天 21:00 的 `schedule-engage.yml` 空跑、燒 Actions 配額、且沒人知道是權限問題。
- **具體改動**：
  1. `.github/workflows/schedule-engage.yml`：註解掉 `schedule:` 觸發，只保留 `workflow_dispatch`（手動），並在註解寫明「待 `threads_manage_replies` 核准後再開啟」。
  2. `src/services/threads.ts` `getPostReplies()`：把 `403`／`OAuthException`（權限類）與其他錯誤分開——權限類拋出可辨識的 `ThreadsPermissionError`，而非靜默 `[]`。
  3. `src/tasks/engage.ts`：捕捉 `ThreadsPermissionError`，回傳一次明確訊息「⚠️ 尚未取得 threads_manage_replies 權限，engage 無法讀取留言」，而非「沒有需要回覆的留言」。
- **驗收標準**：手動跑 `npm run engage` 時，若無權限，輸出明確的權限提示；`schedule-engage.yml` 不再每天自動觸發。
- **工作量**：S（~1 小時）

### ⬜ P0-2　修正 `engagementScore`：把回覆納入，並修掉註解／實作不一致
- **對應**：R3
- **為什麼**：`threads.ts:470` 註解宣稱 `replies×4`，但 `:556` 實作是 `likes×3 + reposts×5 + quotes×4`——**回覆根本沒被計分**。而回覆（尤其「想試」「怎麼預約」這類）是最接近轉換的意圖信號。最高分（11）的貼文正是靠 6 則回覆。
- **具體改動**：
  1. `src/services/threads.ts:556`：改為以**回覆為最高權重**的公式，例如
     `engagementScore = replies × 5 + quotes × 4 + reposts × 4 + likes × 1`
     （理由：回覆＞引用＞轉發＞讚，越接近「主動表達意圖」權重越高）。
  2. 同步修正 `PostInsights` 型別註解（`:470`）使其與實作一致，並把權重理由寫進註解。
- **驗收標準**：含回覆的貼文分數明顯高於只有讚的貼文；型別註解與公式一致。
- **工作量**：S（~30 分）
- **注意**：此改動會改變歷史週報的相對排名邏輯，屬預期行為。

### ⬜ P0-3　週報加入「意圖信號」區塊
- **對應**：R3
- **為什麼**：把週報的焦點從「讚數」轉到「有多少人表達了意圖」。
- **具體改動**：`src/tasks/weeklyReport.ts` 報告產生段落，新增：
  - 「本週回覆總數」「收到回覆數最高的貼文」兩個指標。
  - 數據總覽表加一列「總回覆數」。
- **驗收標準**：週報 Markdown 出現回覆相關統計。
- **工作量**：S（~1 小時）

### ⬜ P0-4　工作流失敗自動告警
- **對應**：R4
- **為什麼**：Token 到期、配額耗盡、發文失敗目前都靜默。自主代理必須回報失敗。
- **具體改動**：在 `schedule-daily-post.yml` / `schedule-report.yml` / `schedule-engage.yml` 各加一個 `if: failure()` 步驟，用 `gh issue create` 開一張標題含工作流名稱與日期的 issue（同名 issue 已存在則改用 comment，避免洗版）。
- **驗收標準**：故意讓某次執行失敗，repo 出現一張描述失敗的 issue。
- **工作量**：S（~1 小時）

## P1 — 拆掉結構性脆弱

### ⬜ P1-1　把不可信的 AI 輸出移出可執行程式碼（`.ts` → JSON + zod 驗證）
- **對應**：健診報告「設定即代碼」風險的根治
- **為什麼**：`brand.ts` / `styles.ts` / `features.ts` 是被 `tsx` 執行的程式碼，AI 用字串替換寫入；一個沒跳脫的單引號就讓整個服務 `SyntaxError` 掛掉。把資料移出程式碼，「壞輸出弄垮 prod」這整類問題直接消失，diff／回滾也變簡單。
- **具體改動**：
  1. 新增 `src/data/brand.json`、`styles.json`、`features.json`（純資料）。
  2. 新增 `src/data/schema.ts`：用 `zod` 定義各檔 schema。
  3. 新增 `src/data/index.ts`：載入 JSON、`schema.parse()` 驗證後 export（驗證失敗則明確報錯並中止，不發出壞內容）。
  4. 改寫 `src/utils/dataUpdater.ts`：讀寫改為 JSON（`JSON.parse` / `JSON.stringify`），移除脆弱的正則字串替換與跳脫邏輯。
  5. 全專案 import 來源從 `data/*.ts` 改為 `data/index.ts`。
- **驗收標準**：所有任務照常運作；故意寫入壞資料時於載入階段被 zod 擋下並明確報錯，而非執行期 `SyntaxError`。
- **工作量**：M（~1 天）
- **依賴**：新增 `zod` 套件。
- **連帶效益**：健診報告「為 dataUpdater 補測試」變得簡單（測 schema 驗證即可）。

### ⬜ P1-2　學習迴路加「信號閘門」：沒有信號就不更新 data 層
- **對應**：R2
- **為什麼**：目前只要貼文數 ≥5 就讓 AI 改寫 brand/styles。但若該週互動全是 0（無變異），AI 是在對噪音學習。應在「互動有足夠變異且可歸因」前，不更新策略。
- **具體改動**：`src/tasks/weeklyReport.ts`：
  1. 計算本週互動分數的變異（例如 `最高分 − 中位數`）。
  2. 若變異低於門檻（例：< 一個可設定的 `MIN_ENGAGEMENT_SPREAD`），**跳過 `applyDataUpdates`**，僅產出報告與「本週信號不足，未更新策略」說明。
  3. 門檻設為常數並加註解說明理由。
- **驗收標準**：對一份全 0 互動的測試資料，週報照出但不產生 data 層 PR。
- **工作量**：S–M（~半天）

### ⬜ P1-3　接上真實轉換指標（追蹤連結 / UTM）
- **對應**：R3、R2（讓迴路有「接近營收」的信號可學）
- **為什麼**：Threads 每篇 insights 只有 views/likes/replies/reposts/quotes，**沒有連結點擊**。要量「有多少人點進 GlowMoment」，必須用帶 UTM 的可追蹤連結，從外部（GA／短連結後台）讀點擊。
- **具體改動**：
  1. `src/data/brand.json`（P1-1 後）新增 `links.primary`，值為帶 `?utm_source=threads&utm_medium=social&utm_campaign=glowpulse` 的連結（或短連結服務）。
  2. autoPost / imagePost 的 prompt 統一引用此連結常數，不再讓 AI 自由生成裸連結。
  3. 文件：在週報或 README 說明如何從追蹤後台讀每週點擊數，人工填入或日後串 API。
- **驗收標準**：發出的貼文連結都帶 UTM；有一個明確管道可看到每週點擊。
- **工作量**：S（~1 小時，不含外部後台設定）

## P2 — 校準投資與長期

### ⬜ P2-1　打通「主動出擊」管道（最高槓桿，但需外部審核）
- **對應**：R1
- **為什麼**：對冷啟動帳號，去別人貼文底下互動是唯一能撬動分發的槓桿。
- **具體改動／行動**：
  1. Meta for Developers → App → Threads API 申請 `threads_manage_replies`（讀自己貼文留言）。
  2. 送 App Review 進階存取，讓 `reply-to` 能自動抓他人公開貼文內容（免手動貼上）。
  3. 權限到位後：恢復 `schedule-engage.yml` 排程（回收 P0-1 的暫停）。
- **驗收標準**：`engage` 能真實讀到並回覆留言。
- **工作量**：行政為主（審核數天），程式碼已就緒。

### ⬜ P2-2　複雜度瘦身
- **對應**：投資校準
- **具體改動**：
  1. 把 `gen-styles` 從 `schedule-report.yml` 每週自動執行移除（改為手動 `npm run gen-styles`），避免 AI 每週自動擴充未經驗證的風格。
  2. 多供應商路由保留，但凍結「風格自動生成／自動改寫」直到有信號（與 P1-2 一致）。
- **驗收標準**：每週排程不再自動新增風格；風格庫變動都經人工。
- **工作量**：S。

### ⬜ P2-3　內容策略：加入「創辦人直球」與短文專屬風格
- **對應**：R3 的數據結論（最高互動來自坦誠的直接邀請）
- **具體改動**：
  1. 在 styles 新增 1–2 個「創辦人直球邀請型」風格（真誠、求協作、零風險邀請）。
  2. 為 `--max-chars 130` 短文建立專屬風格，強制使用誘導留言結尾。
  3. 降低拋光產品廣播在輪替中的比重。
- **驗收標準**：排程中出現創辦人視角貼文；短文都帶誘導留言結尾。
- **工作量**：S–M。

### ⬜ P2-4　核心模組單元測試
- **對應**：健診報告技術負債
- **具體改動**：針對 `data/schema.ts`（P1-1 後）、`publish.ts` 的 `splitContent`、`threads.ts` 的 `parseThreadsPostId` 各補 10–20 個 unit test（建議 `vitest`）。
- **驗收標準**：`npm test` 可跑，涵蓋上述高風險函式的邊界條件。
- **工作量**：M。

## 建議執行順序

```
P0-1 → P0-2 → P0-3 → P0-4   （半天～一天，立即止血）
        ↓
P1-1（JSON+zod，地基）→ P1-2（信號閘門）→ P1-3（UTM）
        ↓
P2-1（申請權限，並行）／ P2-2 ／ P2-3 ／ P2-4
```

P0 各項彼此獨立、可分別出 PR；P1-1 是 P1-2／P2-4 的地基，建議先做。
